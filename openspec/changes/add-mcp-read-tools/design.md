# Design

## Context

Мотивация — в proposal.md, требования — в `specs/`. Что уже есть и задаёт
форму решения:

- **Каркас C++-сервиса** у wallet-report и wallet-ai одинаковый: cpp-httplib,
  `util/` из wallet-common, `docs.cpp` (`/healthz`, `/version`,
  `/openapi.yaml`, `/docs`), `version.hpp.in` с `GIT_COMMIT`, многостадийный
  `Containerfile` (debian bookworm-slim, `BUILD_JOBS=3`), GitHub Actions
  `ci.yml`/`release.yml`/`packages-cleanup.yml`. wallet-mcp копирует его
  целиком, но без libpq: базы у сервиса нет.
- **wallet-common** уже содержит почти всё, что нужно инструментам:
  - `clients/reports_client` — `GET` в wallet-report с Bearer-токеном,
    `url_encode`, метрика ошибок по имени;
  - `expense/resolver::parse_accounts` — разбор `GET /api/reports/accounts`:
    кошельки с `iso_code`/`symbol`/`precision`, категории без системных,
    порядок как в ответе;
  - `expense/text` — `normalize_name` (регистр, `ё`→`е`, пробелы),
    `resolve_name` (точное, затем уникальный префикс, `Ambiguous` со всеми
    кандидатами), `truncate_utf8`;
  - `util/` — `dotenv`, `log` (trace_id), `metrics`, `crypto::sha256`, `hex`,
    `uuid` (v4 для `Mcp-Session-Id`).
- **Сервер не знает пояса и кошелька по умолчанию пользователя.** Даты
  операций — локальное время без пояса. Пояс (`/tz`) и кошелёк по умолчанию
  (`/default`) хранит только wallet-telegram в своей базе, в токене и в
  wallet-report их нет.
- **Отчёты wallet-report** принимают границы как timestamp включительно
  (`from`/`to`), а `/balance` — дату **не** включительно. `eq_currency`
  обязателен везде. Суммы — десятичные строки (`numeric`).
- Гейтвей ждёт ответа апстрима до 30 с, поэтому инструменты должны быть
  синхронными и укладываться с запасом.

## Goals / Non-Goals

**Goals:**
- Тонкий адаптер без состояния, кроме кешей в памяти: перезапуск ничего не
  теряет.
- Каждое число в ответе — из SQL wallet-report или точная десятичная
  операция над такими числами.
- Минимум нового кода: всё, что уже проверено в боте (`resolve_name`,
  `parse_accounts`, клиент отчётов), переиспользуется.

**Non-Goals:**
- Проверка JWT по JWKS в самом сервисе. JWT получен от google-auth по
  внутренней сети и проверяется wallet-report, а сервис его только переносит.
- Общий валидатор JSON Schema. Шесть схем проверяются вручную.
- `structuredContent`/`outputSchema` из новых ревизий MCP, ресурсы (`resources/*`),
  промпты (`prompts/*`), sampling.

## Decisions

### D1. Транспорт: только POST с JSON-ответом
Streamable HTTP разрешает серверу отвечать на POST обычным
`application/json` вместо SSE и отвечать `405` на GET, если серверных
уведомлений нет. Так и делаем. Сервер ничего не стримит, а гейтвей буферизует
ответы целиком, поэтому SSE ничего бы не дал.
*Альтернатива:* SSE ради прогресса долгих вызовов — долгих вызовов нет.

Версии протокола: сервис знает `2025-06-18` и `2025-03-26` и отвечает
запрошенной из них, иначе `2025-06-18`. **Проверить по спецификации на момент
реализации:** нет ли новой ревизии, которую LM Studio уже присылает, и
обязателен ли разбор заголовка `MCP-Protocol-Version` (в `2025-06-18` клиент
шлёт его после рукопожатия). В v1 заголовок принимается и не проверяется.

*Сверено 2026-11-02 (реализация):* последняя ревизия с рукопожатием —
`2025-11-25`, она добавлена первой в список (для tools-сервера с JSON-ответами
отличий нет). Текущая ревизия `2026-07-28` убрала `initialize` и сессии
(`server/discover`, версия в каждом запросе) — в v1 не поддерживается. Чтобы
клиент, умеющий обе ревизии, откатился на рукопожатие, заголовок
`MCP-Protocol-Version` всё же проверяется: незнакомая версия — `400` (так
требует и `2025-06-18`), пустой — как раньше.

### D2. Сессии без состояния
`Mcp-Session-Id` — случайный UUID v4, выдаётся на `initialize` и нигде не
хранится. Спека MCP разрешает серверу не требовать сессию. Личность всегда
берётся из `Authorization` (`mcp-access`), поэтому украденный или подставленный
id ничего не даёт, а рестарт не разрывает клиентов. **Проверить по
спецификации:** клиенты, получившие `404` на неизвестную сессию, переподключаются.
Мы `404` не отдаём, так что этот путь не используется.

### D3. Аутентификация: обмен без проверки подписи у себя
Цепочка: префикс `wmcp_` → SHA-256 токена (hex) как ключ кеша → при промахе
`POST {AUTH_SERVICE_URL}/internal/mcp/token` → `access_token` и `expires_in`.
Время жизни кеша считается от `expires_in` ответа (минус 30 с), без разбора
JWT. Так сервису не нужны ни JWKS, ни `jwt_claims`.
*Альтернатива:* проверять JWT по JWKS. Это лишняя зависимость: подделать
ответ google-auth во внутренней сети не проще, чем обойти сам сервис, а
wallet-report проверяет подпись в любом случае.

- Кеш — `unordered_map` под мьютексом, без ограничения размера с вытеснением:
  токенов у пользователя единицы. Записи с истёкшим сроком вычищаются при
  обращении и раз в N запросов.
- Параллельные промахи по одному токену могут дать два обмена. Это допустимо:
  обмен идемпотентен, а схлопывать запросы (single-flight) ради этого не стоит.
- Повтор при `401` от wallet-report (`mcp-access`) — один, чтобы при смене
  ключа google-auth не было цикла.
- HTTP-клиент к google-auth — новый небольшой модуль в `src/`
  (`reports_client` умеет только GET). Таймауты: соединение 3 с, ответ 5 с.

### D4. Origin не проверяется
Спека MCP требует от серверов Streamable HTTP проверять `Origin` против DNS
rebinding. Угроза там — браузерная страница, обращающаяся к локальному
серверу **без** авторизации. Здесь каждый запрос требует `Bearer wmcp_…`, а
браузер чужой страницы этот токен не знает и не подставит, поэтому `Origin`
в v1 не проверяется. **Проверить по спецификации:** если в будущем появится
анонимный путь (например, OAuth-метаданные), вернуться к этому.

### D5. Аргументы и ошибки: вручную и в два слоя
Для каждого инструмента — функция проверки аргументов: типы, обязательность,
нет лишних ключей. Нарушение схемы даёт JSON-RPC `-32602`, его видит клиент.
Ошибки смысла (дата не существует, `from > to`, имя не найдено или
неоднозначно, неизвестная валюта) дают `isError: true` с текстом: эти
ошибки модель должна прочитать и исправить сама.
*Альтернатива:* общий валидатор JSON Schema — новая зависимость ради шести
плоских схем.

### D6. Даты → границы wallet-report
- `from` → `ГГГГ-ММ-ДД 00:00:00`, `to` → `ГГГГ-ММ-ДД 23:59:59.999999`
  (включительно, как у `periodFrom`/`periodTo`).
- `balance(date)` → `/balance?date=<date + 1 день>`, потому что граница
  `/balance` не включается, а инструмент обещает «на конец дня».
- `list_wallets` — баланс на конец «сегодня» в `MCP_TZ`.
- Проверка существования даты (30 февраля) делается кодом, а не Postgres,
  чтобы модель получила понятный `isError`, а не `Отчёты временно недоступны`.

### D7. Пояс «сегодня» — настройка сервиса `MCP_TZ`
На сервере пояса пользователя нет (см. Context). Варианты:
1. **`MCP_TZ` на сервис** (по умолчанию `UTC`) — выбрано. Владелец стенда
   решил 2026-10-31: UTC (GMT+0) устраивает надолго, в prod переменную не
   задаём. Ошибка в другом поясе — максимум сдвиг «сегодня» на день, а модель
   видит эхо периода.
2. Пояс из wallet-telegram — чужая база, связь сервисов ради одного поля.
3. Пояс в настройках пользователя в google-auth — правильное место, но это
   отдельная фича (см. Open Questions).
Пояс используется в `instructions` и для «сегодня» в `list_wallets` и
`balance`. tzdata в образе нужна (`tzdata` в runtime-стадии `Containerfile`).

### D8. Валюта по умолчанию — первый кошелёк справочника
Кошелёк по умолчанию живёт в базе бота, поэтому берём валюту первого
кошелька из `parse_accounts` (порядок ответа — по имени). Это то же
поведение, что у бота без выбранного кошелька. Модель всегда видит
`currency` в ответе и может передать нужную явно.
*Альтернатива:* самая частая валюта среди кошельков — менее предсказуемо при
равенстве, а польза сомнительна.

### D9. Справочник счетов — кеш на 60 с по пользователю
Почти каждый инструмент сначала разрешает имена или валюту через
`GET /api/reports/accounts`. Ответ кешируется по SHA-256 MCP-токена на 60 с,
как у бота. Ненайденное имя сбрасывает кеш и повторяет поиск один раз:
категорию могли только что создать в приложении.

### D10. Точная десятичная арифметика — свой маленький модуль
`total` по выбранным категориям, `delta` и `total_before` — сложение и
вычитание строк `amount_eq`. В wallet-common десятичного типа нет, а `double`
даёт `0.1 + 0.2 = 0.30000000000000004` — для денег так нельзя.
- Модуль `src/decimal.*`: разбор строки `[-]цифры[.цифры]` в целое
  `__int128` с масштабом 10^8 (`operation.amount` — `numeric(20,8)`, 20 знаков
  целиком влезают в 128 бит), сложение и вычитание, вывод с числом знаков,
  равным максимальному у слагаемых, и без хвостовой точки.
- Остаётся в `src/`, а не в wallet-common: по правилу wallet-common код,
  нужный одному сервису, туда не выносится. Если понадобится второму —
  перенос.
- Складывает сервис, а не модель, и только строки, которые уже посчитал SQL,
  поэтому правило «суммы считает SQL» не нарушается: сервис только сводит
  выборку по нескольким категориям в одну строку.
*Альтернатива:* запрашивать сумму по нескольким категориям у wallet-report —
понадобился бы ещё один эндпоинт и миграция ради сложения 2–5 строк.

Сравнение периодов (`compare_*`) делается **двумя** вызовами
`/expense-structure` (основной и сравниваемый период без `cmp_*`): ответ с
`cmp_*` даёт доли (`pct_before`), но не суммы категорий в периоде сравнения.

### D11. Форма ответа инструмента
`content[0].text` — компактный JSON: короткие ключи, суммы строками,
отформатированными по `precision` валюты, без uuid и `icon_sha256`. Пример
`spending_by_category`:
`{"period":{"from":"2026-09-01","to":"2026-09-30"},"currency":"RUB","rows":[{"category":"Няня","amount":"32000.00"}],"total":"32000.00","incomplete":false}`.
Компактность важна для контекста 8B-модели в LM Studio.

### D12. Карта инструментов на wallet-report

| Инструмент | Вызовы wallet-report |
| --- | --- |
| `list_wallets` | `accounts` (кеш), `balance?date=<завтра>` |
| `list_categories` | `accounts` (кеш) |
| `spending_by_category` | `accounts` (кеш), `expense-structure` ×1 или ×2 |
| `income_expense_by_month` | `accounts` (кеш, валюта по умолчанию), `income-expense-by-month` |
| `balance` | `accounts` (кеш), `balance?date=<date+1>` |
| `search_operations` | `accounts` (кеш), `operations` с `category_uuid`/`wallet_uuid`/`kind`/`q`/`limit` |

Таймаут одного вызова wallet-report — 10 с, в сумме инструмент укладывается
в 30 с гейтвея.

### D13. Логи и метрики
Имена метрик — в спеке `service-endpoints`. Ошибки клиента отчётов — счётчик
`mcp_reports_errors_total{kind}` через параметр `make_http_api`. В access-лог
не пишутся тела запросов и ответов `/api/mcp/`: в них суммы и комментарии.
Это отличие от wallet-report, у которого тело ответа идёт в debug-лог.

## Risks / Trade-offs

- [Комментарии операций попадают в контекст модели и могут содержать
  инструкции (prompt injection)] → у инструментов нет записи и чужого доступа,
  поэтому худшее — неверный ответ. Комментарий обрезается до 120 байт.
- [Кеш JWT переживает отзыв MCP-токена до 5 минут] → это заявленная цена
  (отзыв действует максимум через `expires_in`), она записана в proposal
  google-auth.
- [`MCP_TZ` неверен для пользователя в другом поясе] → эхо периода в ответе.
  Хранение пояса пользователя на сервере отложено (D7).
- [Сальдо вместо суммы трат: модель читает отрицательный итог как «потратил»]
  → `search_operations` по умолчанию `kind=expense`, сальдо только при явном
  `kind: "any"` и с пояснением в описании инструмента (спека `wallet-tools`).
- [8B-модель путает аргументы и даты] → строгие схемы с `-32602`, понятные
  `isError`, эхо периода. Качество tool calling проверяется вручную в LM Studio
  (последняя задача), eval — позже.
- [Новые ревизии протокола MCP] → в D1 и D2 отмечено, что сверить по
  спецификации, а версии поддерживаются списком.
- [`search_operations` зависит от changes в wallet-api и wallet-report] →
  до их выката инструмент отвечает `isError` «поиск пока недоступен», если
  wallet-report вернул `400` на неизвестные фильтры. Остальные пять
  инструментов работают на текущем API.

## Migration Plan

1. Новый репозиторий `WalletTransactions/wallet-mcp`, CI собирает образ в
   `ghcr.io`.
2. Выкат по порядку фичи: google-auth (`add-mcp-personal-tokens`) и wallet-api
   (`add-operations-filter-functions`) → wallet-report → **wallet-mcp** →
   wallet-gateway (`/api/mcp/`, `WALLET_MCP_URL`) → wallet-web (выпуск токена).
   Подключение к стенду — change `wallet-infra/add-wallet-mcp-service`.
3. Откат: убрать маршрут из гейтвея или остановить контейнер. Данных у
   сервиса нет, отзывать токены не нужно. Без гейтвея к нему никто не
   достучится.
