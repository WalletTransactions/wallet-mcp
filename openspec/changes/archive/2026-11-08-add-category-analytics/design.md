# Design

## Context

- Инструменты собраны в `src/tools.cpp`: реестр `build_registry()`,
  разбор аргументов в два слоя (схема → `-32602`, смысл → `isError`, D5
  архивного `add-mcp-read-tools`), имена → uuid через справочник `accounts`
  с кешем 60 с (D9).
- `spending_by_category` уже сводит строки `/expense-structure` точной
  десятичной арифметикой (`src/decimal.*`, D10): при выбранных категориях
  `total` — сумма строк, при всех — `total_eq` из SQL. Деления в модуле нет.
- Ответ — компактный JSON для контекста 8B-модели (D11).
- Новые данные дают эндпоинты парного change wallet-report
  `add-category-month-analytics` (см. его specs): матрица
  `/expense-by-category-by-month`, `op_count` в `/expense-structure`,
  `exclude_category_uuid` в `/operations`.

## Goals / Non-Goals

**Goals:**
- Средние в месяц, сезонность и «всё, кроме…» без арифметики модели.
- Ответы, которые помещаются в контекст маленькой модели.

**Non-Goals:**
- Группы категорий — отдельный change (данные в wallet-api, синк, клиенты).
- Расхождение `income_expense_by_month` и сумм по категориям (ноги
  перевода) — описано в design wallet-report, здесь не правится.
- Медиана, тренды, прогноз — пока нет вопросов, которые без них не решаются.

## Decisions

### D1. Карта новых вызовов на wallet-report

| Инструмент | Вызовы wallet-report |
| --- | --- |
| `spending_by_category_by_month` | `accounts` (кеш), `expense-by-category-by-month` ×1 |
| `spending_by_category` | как раньше; `op_count` читается из того же ответа `expense-structure` |
| `search_operations` | `operations` с `exclude_category_uuid` вместо `category_uuid` |

Итог считает не модель: суммы клеток «категория × месяц» и `op_count` —
агрегаты SQL; сервис только сводит выбранные клетки, как D10 сводит строки
категорий. Без `categories`, `exclude_categories` и `months_of_year` `total`
берётся прямо из `total_eq` ответа.

*Альтернатива:* фильтры категорий и месяцев года на стороне wallet-report.
Отвергнута: это сложение уже готовых агрегатов, ради него не нужны новые
параметры SQL-функции и второй контракт.

### D2. `months_of_year` фильтрует клетки, а не меняет период

Период остаётся непрерывным (`from`..`to`), wallet-report отдаёт все месяцы;
сервис отбрасывает клетки, чей месяц не в списке, и считает делитель только
по выбранным месяцам. Так «лето против остальных» — два вызова с одним и тем
же периодом и дополняющими списками, и их `total` в сумме дают итог периода.

### D3. Делитель `months` — доля месяцев по дням, с двумя знаками

Для каждого календарного месяца, который задевает период (и который выбран),
доля = дни месяца внутри `from`..`to` / дни в месяце. `months` — сумма долей,
округлённая до 0.01 и выведенная строкой. `avg_per_month` = сумма / `months`
(уже округлённый — чтобы модель и пользователь могли перепроверить деление по
числам из ответа), округление до precision валюты, половина — от нуля.

- Период «последние два года» со сдвигом (2024-11-05..2026-11-04) даёт ровно
  24.00: крайние месяцы складываются в один.
- `months` = 0 невозможен: период включает хотя бы один день, а пустой
  выбор месяцев года (`months_of_year`, ни один из которых не попал в
  период) — `isError: true` «В периоде нет выбранных месяцев.».

*Альтернативы:* число задетых месяцев (25 для того же периода — среднее
занижено на 4 %) или дни / 30.4375 (не совпадает с целыми месяцами для
периода «июнь–август»). Отвергнуты.

### D4. Деление в `decimal`

`decimal::div(const Decimal& a, const Decimal& b, int precision)` →
`std::optional<std::string>`: `a.units × 10^p / b.units` в `__int128` с
округлением половины от нуля; `nullopt` при `b = 0` или переполнении (на
суммах до 10^12 и делителе с масштабом 10^8 переполнения нет — проверяется
до умножения). `nullopt` в ответе — `avg_per_month: null`.

### D5. `exclude_categories`

Разрешение имён — тем же `resolve_all`, системные категории в нём не
участвуют (Transfer исключить нельзя — как и выбрать). Совместно с
`categories` — `isError` до вызова wallet-report.

- `spending_by_category` и новый инструмент: строки — все категории ответа,
  кроме исключённых; `total` — точная сумма оставшихся строк (D10).
- `search_operations`: uuid идут в `exclude_category_uuid`; параметр
  считается фильтром — итог есть и при `kind: "any"`.

### D6. `by_month` только при заданных `categories`

Худший случай без фильтра — ~90 категорий × 36 месяцев, до ~50 КБ JSON —
больше контекста 8B-модели. Модель, которой нужна помесячная разбивка,
сначала узнаёт категории (`list_categories` или ответ без `by_month`), затем
просит разбивку по нескольким. Для средних и сезонности разбивка не нужна —
хватает `avg_per_month` и `months_of_year`.

*Альтернатива:* аргумент `by_month: true`. Отвергнута: модель включала бы
его и без фильтра — тот же объём.

### D7. Поля ответа `spending_by_category`

Добавляются `count`, `avg_per_month` в строки и `months`, `avg_per_month`
(итога) в ответ; с периодом сравнения — `count_before`,
`avg_per_month_before`, `months_before`. Существующие поля и порядок ключей
не меняются — ответы, на которые опираются LM Studio и eval, остаются
валидными. `count` итога — сумма `op_count` строк (целые, без потерь).

### D8. Правки вне wallet-mcp

- **wallet-report** + **wallet-api** — парный change
  `add-category-month-analytics` (новый эндпоинт, `op_count`,
  `exclude_category_uuid`, миграция).
- **google-auth, wallet-gateway, wallet-common, wallet-web, wallet-infra** —
  не нужны: `scope reports:read` уже покрывает новый эндпоинт, путь под
  `/api/reports/*`.

## Risks / Trade-offs

- [wallet-mcp выкатили раньше wallet-report] → новый инструмент получает 404
  → «Отчёты временно недоступны…», а `op_count` отсутствует → в
  `spending_by_category` `count: null`, остальное работает. В tasks — порядок
  выкладки и проверка на test.
- [Модель путает `months_of_year` с периодом и передаёт летние даты] →
  описание инструмента прямо говорит «период — непрерывный, месяцы года —
  фильтр»; eval-вопрос «насколько лето дороже» в живом прогоне.
- [Семь инструментов вместо шести — модель чаще выбирает не тот] → описания
  различают: `spending_by_category` — «итоги за период»,
  `spending_by_category_by_month` — «средние, по месяцам, сезонность».

## Migration Plan

1. wallet-api миграция → wallet-report (парный change), проверка на test.
2. wallet-mcp. Откат — предыдущим образом: семь инструментов исчезают, шесть
   работают как раньше (новые поля wallet-report им не мешают).
